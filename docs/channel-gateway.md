# Pulse support channels

This optional Python service gives Pulse AI private, fixed support menus in English, Arabic, Thai and Simplified Chinese. It supports account questions, privacy navigation and a route to a human. It runs separately from the Telegram bot with its own start command. All three switches default to false.

## Run and verify

Use Python 3.12 and install the two gateway dependencies. The tests exercise local HTTP, synthetic callbacks, a temporary SQLite volume and mocked provider sends.

```sh
python -m pip install -r pulse-channels-requirements.txt
python -m unittest discover -s tests -p test_pulse_channels.py -v
PYTHONPATH=. python tests/run_channel_trials.py
python -m pulse_channels
```

The server binds the value of `PORT` or 8080. `GET /healthz` returns `{"ok":true}` for process liveness, including when every adapter is disabled. An enabled adapter requires each of its credentials at startup. A missing setting produces its name in the error.

Place this process behind a TLS terminator with a valid public certificate. Disable raw requests, query strings, message bodies, cookies and headers in proxy access logs, traces and error collection. WhatsApp verification secrets travel in GET query parameters. The app disables its HTTP access log and returns `Cache-Control: no-store`. Attach a protected persistent volume for pending WhatsApp and LINE deliveries. Run one service replica against the volume. On Railway, give the gateway service its own install and start commands and volume and preserve the existing Telegram service configuration.

## Settings

| Channel | Settings |
|---|---|
| Shared WhatsApp and LINE | `PULSE_CHANNEL_STATE_DIR` absolute mounted directory, `PULSE_CHANNEL_STATE_KEY` stable standard Base64 encoding of 32 random bytes, `PULSE_SUPPORT_URL` approved operator-owned HTTPS page with human support or `PULSE_SUPPORT_CONTACT` monitored email/phone. The page URL must omit user identifiers, query and fragment. |
| WhatsApp | `PULSE_WHATSAPP_ENABLED=true`, `WA_APP_SECRET`, `WA_VERIFY_TOKEN`, `WA_ACCESS_TOKEN`, `WA_PHONE_NUMBER_ID`, `WA_BUSINESS_ACCOUNT_ID`, `WA_GRAPH_VERSION`. Pin a supported Graph version on the Meta app. |
| LINE | `PULSE_LINE_ENABLED=true`, `LINE_CHANNEL_SECRET`, `LINE_CHANNEL_ACCESS_TOKEN`, `LINE_DESTINATION_ID` (the bot's userId returned by `GET /v2/bot/info`). |
| WeChat Official Account | `PULSE_WECHAT_ENABLED=true`, `WECHAT_CALLBACK_TOKEN`, `WECHAT_ENCODING_AES_KEY` (Tencent's 43-character value), `WECHAT_APP_ID`, `WECHAT_ORIGINAL_ID` (the OA's Original ID in inbound ToUserName), `WECHAT_SUPPORT_CONTACT` (market-approved local monitored phone/email). Optionally set `WECHAT_APPROVED_LOCAL_SUPPORT_URL` to a separately reviewed, locally hosted support page. |

Use a secret manager to generate and provision the state key and the providers' credentials. Keep the state key stable across process restarts. A key mismatch on an existing volume fails startup. Plan volume/key migration together. WeChat uses only its dedicated local contact and optional local URL. It never reuses the international support page.

## Provider setup

1. **WhatsApp Cloud API.** Create a Meta business app with WhatsApp, select a WABA and business phone number, and issue a scoped token with messaging permission for that number. Set the callback to `https://<gateway>/webhooks/whatsapp`, enter the same verify token and subscribe the app to the WABA's `messages` field. The gateway verifies Meta's GET challenge and SHA-256 HMAC over the original POST bytes, checks the WABA and phone number, and sends an individual text reply through `POST /{graph-version}/{phone-number-id}/messages`. It prefers the business-scoped user ID; the phone-number path is used when only a number was supplied. Signed group, status and unsupported events receive HTTP 200 with no active send. The support menu is a separate use case from the Telegram health assistant. Verify the approved business purpose, human escalation, recipient-market rules and the target WABA before activation. [Webhooks](https://developers.facebook.com/documentation/business-messaging/whatsapp/webhooks/overview/) · [User identifiers](https://developers.facebook.com/documentation/business-messaging/whatsapp/business-scoped-user-ids/) · [Messaging policy](https://business.whatsapp.com/policy)
2. **LINE Messaging API.** Create a LINE Official Account, enable Messaging API in OA Manager with the operator's own provider, enter `https://<gateway>/webhooks/line` in Developers Console, verify, enable webhooks and redelivery. Turn off conflicting auto-replies and leave group invitations off. The adapter verifies the original bytes with `X-Line-Signature`, checks the destination and active one-to-one event, then sends a canned text via the one-use reply token. Signed verification requests with an empty events array receive HTTP 200. Recipients can type the exact words listed in the menu or use matching rich-menu postback data. [Setup](https://developers.line.biz/en/docs/messaging-api/getting-started/) · [Verification](https://developers.line.biz/en/docs/messaging-api/verify-webhook-signature/) · [Reply](https://developers.line.biz/en/reference/messaging-api/#send-reply-message) · [Thailand API terms](https://terms2.line.me/official_account_api_terms_th)
3. **WeChat Official Account.** Use an eligible Official Account with server callback management enabled. Configure `https://<gateway>/webhooks/wechat` with the matching token and EncodingAESKey, choose Safe Mode, and use an environment approved for the target users. The enrollment GET validates the signed token/timestamp/nonce and echoes the challenge. An encrypted signed echo is also understood. The data route requires an AES-encrypted POST, checks the signature, app ID and receiver, and produces an encrypted passive XML reply on the same HTTP request. No access-token exchange, proactive message or group access is required for this single route. The gateway accepts callbacks with server timestamps within five minutes; keep the clock synchronized. Verify the account's actual webhook, supported feature permissions and reviewed local landing page before turning on real traffic. [Developer onboarding](https://developers.weixin.qq.com/doc/offiaccount/Basic_Information/Access_Overview.html) · [Encrypted messages](https://developers.weixin.qq.com/doc/offiaccount/Message_Management/Message_encryption_and_decryption_instructions.html) · [Passive replies](https://developers.weixin.qq.com/doc/offiaccount/Message_Management/Passive_user_reply_message.html)

For the first provider-console test, use dedicated test accounts and a neutral menu word. Confirm authentication, callbacks, device receipt, locale and the human-support destination independently. An accepted API request or successful console challenge alone does not establish end-to-end delivery. Activate the channels individually after account eligibility, local processing and platform approvals are confirmed.

## Inbound data and delivery

* The service compares text with exact support keywords locally. Unrecognized private text or media receives a fixed message about the support scope and local emergency services. The user's content never appears in a response. Media files, captions, audio, location coordinates and medical records are never retrieved or passed to a model. Ignore LINE groups and rooms, standby and unsend events, WhatsApp groups, status updates and exact multilingual opt-out commands. There are no proactive subscriptions, alerts or reminders in this service. The native messaging provider still receives what its user types; publish the scope before users begin a chat.
* LINE and WhatsApp acknowledge valid actionable batches only after the volume has committed the work. Each channel uses a separate SQLite database with its own derived encryption and HMAC keys. A keyed digest of the provider's event ID prevents duplicates. During a pending send, the worker retains an AES-GCM-encrypted reply destination or token and fixed language/menu choices. Recipient data, raw messages and credentials never appear in app logs. Completing, expiring or abandoning a job clears its encrypted routing field. The worker retains only the event digest, timing, attempts and delivery state for up to eight days of active operation. Protect backups and set their retention separately.
* One worker per enabled outbound channel sends the approved text. A pre-connection failure or explicit HTTP 429 can retry within the permitted window, up to four attempts. The worker honors Retry-After and caps processing at the platform deadline. A timeout after submission, an HTTP 408/5xx, or a crash after claiming a job leaves the outcome unknown. These submissions are held to avoid duplicates. A send accepted by the provider records `accepted`; a user can still have blocked the account. WhatsApp uses a one-minute margin before the inbound message's 24-hour service window closes. LINE uses a five-second margin on the reply token; eligible redeliveries are bounded by the original event's 20-minute limit. No fallback push is sent.
* WeChat returns only a passive response. When Tencent redelivers the same authenticated callback, each request receives the same fixed menu meaning and fresh encrypted envelope. There is no outbound network send, stored OpenID or persistent callback side effect. Tencent determines which acknowledged passive response appears on the device.
* `GET /healthz` only verifies the process. Inspect aggregate counts of `pending`, `sending`, `accepted`, `rejected`, `unknown` and `expired` on each mounted database, and check the oldest pending age without retrieving row contents. Repeated unknown, expired or rejected jobs should trigger an operational investigation with a synthetic message. Pause inbound before draining a volume. The included local replay measures protocol behavior, not throughput under provider quotas.

## Scope of this pilot

The adapters provide static business support. Telegram entitlements, open-ended health Q&A, OpenAI, Care Finder, uploaded health media and medication reminders stay outside the new callbacks. Any separately reviewed private care portal must supply its own authentication, consent and approved health-data processing. Keep support links free of chat IDs, patient identifiers and tracking parameters.
